# 统一战役工作区与私人测试构建设计

## 状态

本设计于 2026-07-18 经用户选择方案 1 后确认。

它补充并修正 `2026-07-16-campaign-workspace-refactor-design.md`：保留聊天优先、服务端权限权威和四领域工作区原则，将原“队伍”领域收敛为“角色”，并明确 DM 无需绑定角色、统一完整角色卡权限、Character 同步时序及私人测试资料构建契约。

## 目标

- 战役继续以群聊为默认入口，不引入场次启动步骤。
- 玩家在一个战役中绑定一个玩家角色；DM 无需绑定角色。
- DM 可在旁白、NPC 和临时角色之间快速切换当前发言身份。
- 战役中心稳定分为概览、角色、档案、记录。
- 聊天头像、战役角色目录和完整角色卡使用同一 Character 数据源和权限判定。
- 角色创建、角色切换或归档后，聊天和角色目录立即一致。
- 当前档案接口不可用时给出可操作的版本提示，不暴露原始 HTTP 错误。
- 本地私人测试版默认内嵌并验证私有资料；公开构建继续保持空资料占位。
- 修复子职业选项在资料构建、安装及角色创建链路中的丢失问题。

## 非目标

- 本阶段不实现战斗轮次、地图、Token、视野或自动伤害结算。
- 不引入公开资料市场或自动下载商业规则内容。
- 不把客户端 Player/DM 模式当作战役权限来源。
- 不设计复杂的逐字段角色可见性规则。
- 不新增独立 DM 后台。
- 不自动删除临时角色；只提供明确、快速的归档和批量清理操作。

## 已确认根因

### DM 发言身份不可用

服务端创建的 NPC 和临时角色允许 `ownerUserId` 为空，表示由战役主持人共同管理。客户端身份选择器却只保留 `ownerUserId == currentUserId` 的角色，因此创建成功后无法再次选择。

### 角色目录状态陈旧

创建临时角色后，客户端只刷新工作区上下文，没有刷新 `CampaignCharacterController` 的 Character 缓存。聊天当前身份可能已改变，但角色目录仍看不到新角色。

### 档案接口返回 Cannot GET

当前运行中的 Docker 服务端镜像早于档案控制器实现，镜像内的编译产物没有相关路由。客户端直接展示底层 HTTP 文本，既不能恢复，也不能说明升级方法。

### 私人资料测试构建不可靠

- Web 预览脚本执行普通公开构建，内置资料实际为 `{}`。
- 私人构建脚本使用 Windows PowerShell 默认编码读取 UTF-8 JSON，可能损坏中文及 JSON 结构。
- APK 脚本依赖不存在的聚合 bundle，与另一套现场聚合脚本重复。
- 内置资料安装异步启动但未作为应用初始化门槛，角色创建可能早于安装完成。
- 安装器只比较包版本和条目数，不比较内容哈希，同版本修订可能被跳过。

原始私有资料目录可以使用 UTF-8 正常解析。当前包包含职业、子职业和 `subclassOf` 关系，战士 3 级也包含 `optionType=subclass` 的必选项。因此修复重点是构建、安装和角色创建消费链路，不重新提取正文。

## 权限模型

### 权威来源

服务端 `CampaignMembership.role` 是权限权威来源。客户端设置中的 DM/Player 模式只改变全局工作区，不授予战役权限。

服务端为当前成员计算能力集，至少包含：

- `canManageCampaign`
- `canInviteMembers`
- `canManageCharacters`
- `canEditAnyCharacter`
- `canCreateArchive`
- `canManageArchive`

客户端只根据能力集展示操作，服务端仍在每个写接口重新鉴权。

### 角色卡权限矩阵

| 查看者 | 自己绑定的玩家角色 | 其他玩家角色 | NPC / 临时角色 |
| --- | --- | --- | --- |
| player | 完整查看并编辑 | 完整只读 | 完整只读 |
| owner / dm | 完整查看并编辑 | 完整查看并编辑 | 完整查看并编辑 |

“自己的角色”由战役成员绑定关系和角色所有者共同判定，不能只比较客户端当前选择。

### DM 无绑定角色

owner 和 dm 的 `boundCharacterId` 可为空且不影响进入战役、发言和管理。DM 的当前发言身份是独立的可空 `activeSpeakerCharacterId`：

- 空值表示 DM 旁白。
- 非空值必须指向当前战役中活跃、可由 DM 操作的 NPC、怪物、同伴或临时角色。
- DM 不借用玩家角色作为常规发言身份，避免把玩家角色归属和扮演身份混为一谈。

player 必须绑定一个有效玩家角色后才能发送角色内“说/做”消息；未绑定时只允许场外消息和阅读。

## 统一 Character 模型

### 类型与生命周期

Character 类型继续使用：

- `playerCharacter`
- `npc`
- `monster`
- `companion`

生命周期使用：

- `persistent`
- `temporary`
- `archived`

临时角色不是另一套数据结构，只是 `lifecycle=temporary` 的普通战役 Character。转为长期 NPC 只改变生命周期，角色 ID、消息归属和审计记录保持不变。

### 单一客户端状态源

完整角色目录以 `CampaignCharacterController` 为唯一状态源。工作区上下文可以保存轻量身份摘要，但不能独立维护另一份可编辑 Character 列表。

所有 Character 写操作通过同一个协调方法完成：

1. 调用服务端写接口。
2. 拉取 Character 增量直到当前 revision。
3. 刷新工作区上下文和当前发言身份。
4. 一次性通知 UI 更新。

创建、编辑、绑定、切换身份、转长期和归档都使用该时序。任何页面不得自行拼接一份局部 Character 缓存。

## 聊天室设计

### 输入区

输入区保持单行主结构：

1. 当前身份头像或 DM 旁白图标。
2. 紧凑的“说/做”图标分段控件。
3. 自适应输入框。
4. 加号工具入口。
5. 发送按钮。

“说/做”不显示可见文字：

- “说”使用对话气泡图标。
- “做”使用动作图标。
- 两者保留 Tooltip、Semantics label、选中态和键盘焦点。

### 身份面板

玩家点击头像：

- 打开自己角色的快捷摘要。
- 可继续进入完整角色卡。
- 不显示身份切换和 DM 管理操作。

DM 点击头像：

- 首项为“DM 旁白”。
- 分类显示常用 NPC、临时角色和其他 DM 可控角色。
- 支持搜索或按名称快速定位，不引入多层页面。
- 支持就地新建临时角色。
- 每个角色提供“打开角色卡”；管理动作放在角色卡或角色目录，不把面板做成完整后台。

### 消息头像

所有角色消息头像都通过统一 `openCampaignCharacterSheet(characterId)` 打开完整角色卡。系统消息或无 Character 的 DM 旁白不伪造角色卡入口。

角色卡是否可编辑由权限矩阵计算，不能由不同入口分别实现。

## 战役中心信息架构

### 概览

概览承担成员和战役入口信息：

- 战役名称、头像、简介和规则系统。
- owner / DM 信息。
- 当前成员数、角色数、最近活动。
- 成员列表：用户名、角色头像、绑定角色名和成员身份。
- owner / dm 可见的邀请码区域：创建、复制、系统分享和失效时间。
- 普通玩家不加载也不显示邀请码管理接口。

邀请码默认采用“当前可用邀请码”展示，不在首屏堆叠历史邀请码。需要管理历史时使用溢出菜单或详情对话框。

### 角色

原“队伍”标签改为“角色”，不再混放成员和邀请码。默认分类：

- 玩家角色
- NPC
- 临时角色
- 其他角色
- 已归档角色

分类为空时不显示空分组。每个角色条目显示头像、名称、类型、生命环和必要状态；点击整个条目打开完整角色卡。

DM 可在页面内：

- 新建 NPC 或临时角色。
- 编辑任意角色。
- 将临时角色转为长期 NPC。
- 归档角色。
- 批量选择并归档临时角色。

玩家只看到允许查看的角色和自己的编辑入口，不显示 DM 操作。

### 档案

档案继续承载地点、线索和共享资料条目。客户端先使用服务端能力或构建信息判断支持状态：

- 支持时正常加载。
- 服务端版本过旧时显示“服务端版本过旧，请升级后使用战役档案”。
- 网络失败时显示重试。
- 403 时显示权限说明。
- 404 路由缺失不得直接显示 `Cannot GET`。

服务端部署和本地预览必须重建镜像，而不是只重启旧容器。

### 记录

记录继续提供聊天搜索、检定和系统事件。成员管理不放入此页。

## 完整角色卡导航

建立一个统一入口：

```text
openCampaignCharacterSheet(characterId, viewerCapabilities)
```

它负责：

- 拉取或读取完整角色投影。
- 计算 `canEdit`。
- 打开同一个完整角色卡页面。
- 写入成功后触发统一 Character 同步。

以下入口必须全部使用它：

- 聊天消息头像。
- 输入栏当前身份头像。
- 战役中心角色条目。
- 概览中的成员绑定角色。

废弃只能显示少量字段且权限不一致的重复快捷角色卡；如需快捷摘要，它只能作为完整入口前的展示组件，不拥有独立编辑逻辑。

## 档案 API 与版本兼容

服务端继续使用现有战役档案路由，不创建第二套路由。增加轻量构建能力信息，至少包含：

- 服务端应用版本。
- API 版本。
- 支持的功能标识，例如 `campaignArchives`。

客户端进入战役时缓存能力信息。功能标识用于生成友好提示，但服务端权限响应仍为最终结果。

部署验收必须包含：

- 新镜像构建时间或版本与源码一致。
- 档案路由 e2e 测试。
- Compose 启动后 API 冒烟测试。

## 私人测试资料构建

### 公开与私人边界

公开仓库继续跟踪空的 `assets/bundled_content.json`，不提交商业规则正文或生成后的私人 bundle。

本地私人测试构建从被 `.gitignore` 排除的 `private-imports/phb-2024-v2/` 读取内容。生成的 Web、APK 或桌面测试产物仅供用户本地小范围测试，不作为公开发布产物。

### 唯一构建入口

合并现有重复脚本为一个私人测试构建器，支持：

- `web`
- `apk`
- 后续桌面目标

预览脚本默认调用私人 Web 测试构建器。公开构建仍通过明确的普通 Flutter 构建命令执行。

私人构建器必须：

1. 以 UTF-8 无 BOM 读取 manifest 和全部条目。
2. 验证每个 JSON 文件可解析。
3. 验证 `entryCount`。
4. 验证所有引用和 `subclassOf` 关系。
5. 对每个包含子职业选择的职业执行真实 `RuleChoiceResolver` 验证。
6. 聚合 bundle 并临时注入资产。
7. 执行 Flutter 构建。
8. 在 `finally` 中恢复公开空资产。
9. 输出产物路径、SHA-256 和资料包内容哈希。

任何验证失败都必须停止构建，不能带警告继续。

### 应用安装门槛

应用初始化必须等待 `BundledContentInstaller` 完成后再开放资料库和角色创建入口。安装状态包括：

- 无内置资料：允许进入，资料库为空。
- 正在安装：显示轻量初始化状态。
- 安装成功：刷新资料库后开放角色创建。
- 内置资料无效：测试构建显示阻断错误，不能静默跳过。

安装器使用包 ID 和内容哈希判断是否需要替换。版本和条目数用于展示与校验，不能代替内容哈希。

## 子职业端到端契约

一个可用子职业选择必须同时满足：

1. 职业等级 progression 包含 `optionType=subclass` 的 choice。
2. 子职业条目类型为 `subclass`。
3. 子职业包含 `subclassOf -> classEntryId` 关系。
4. 导入器保留 relations。
5. 本地仓库查询同时返回职业和子职业条目。
6. 角色创建器以真实职业 entry ID 调用 `RuleChoiceResolver`。
7. UI 在选项为空时区分“包未安装”“关系断裂”和“确实无选项”。

测试至少覆盖：

- 私有包中 12 个职业的子职业 choice 都能解析出至少一个选项。
- 战士 3 级可以解析出其全部有效子职业。
- 选择子职业后，子职业自身 progression 和 grants 会进入角色规则投影。
- 同一内容哈希不会重复安装；相同版本但不同哈希会替换安装。
- 角色创建不能早于内置资料初始化完成。

## 错误处理

用户界面不得显示裸异常、路由文本、Character ID、revision 或同步游标。

统一错误分类：

- `networkUnavailable`
- `serverOutdated`
- `permissionDenied`
- `validationFailed`
- `conflict`
- `unknown`

每类错误提供简短说明和一个明确恢复动作，如重试、升级服务端或返回编辑。

## 测试策略

### Flutter

- DM 无绑定角色仍可发送旁白。
- DM 身份面板显示 owner 为空的 NPC 和临时角色。
- 玩家身份面板不能切换角色。
- 新建临时角色后聊天身份和角色目录同时刷新。
- 说/做控件只显示图标且具有 Semantics label。
- 概览显示成员和邀请码；角色页不显示成员列表。
- 所有角色入口打开同一完整角色卡。
- 玩家可编辑自己的角色、只读他人；DM 可编辑全部角色。
- 档案路由缺失显示服务端过旧提示。
- 私人资料安装和子职业解析端到端测试。

### 服务端

- DM 不需要 `boundCharacterId`。
- player 的角色发言必须来自其绑定角色。
- DM 只能把 `activeSpeakerCharacterId` 设置为可管理的非玩家角色或空值。
- owner / dm 可编辑任意战役角色。
- player 只能编辑自己的角色。
- 角色查看、邀请和档案接口按角色正确授权。
- 档案路由和服务端能力信息 e2e。

### 构建与部署

- 私人 Web 构建包含非空 bundle。
- 私人 APK 构建包含相同内容哈希。
- 公开构建资产仍为 `{}`。
- 构建失败后也能恢复公开资产。
- Docker 重新构建后档案 API 冒烟测试通过。

## 实施顺序

1. 权限矩阵、统一 Character 同步协调器和回归测试。
2. DM 发言身份与输入栏重构。
3. 战役中心概览和角色页重构。
4. 统一完整角色卡导航及编辑权限。
5. 档案 API 兼容提示、服务端构建能力和镜像验证。
6. 私人资料构建器、安装门槛和子职业端到端验证。
7. 全量验证、私人 Web 预览和 APK 测试构建。

## 验收标准

- DM 不绑定角色即可进入战役、发送旁白并切换 NPC / 临时角色。
- DM 新建临时角色后，无需刷新页面即可在身份面板和角色页看到它。
- 概览可分享邀请码并查看成员；角色页只管理和查看角色。
- 聊天头像和角色条目均打开完整角色卡。
- 玩家可编辑自己的角色且不能编辑他人；DM 可编辑全部战役角色。
- 说/做控件无可见文字，仍满足可访问性要求。
- 档案页不再出现裸 `Cannot GET`，当前服务端重建后接口可用。
- 私人测试 Web 和 APK 默认包含通过校验的资料包。
- 角色创建可选择有效子职业，且子职业规则继续参与角色投影。
- 公开仓库和公开构建不包含私人规则正文。
